## 1. Electrical Safety & Prototype Disclaimer

> [!CAUTION]
> **ELECTRICAL HAZARD & SAFETY NOTICE:**  
> This system is designed to monitor Alternating Current (AC) circuits operating at **hazardous mains voltages (110V – 240V AC)**.
> - Mains AC voltages carry severe risks of **lethal electric shock, electrocution, electrical fires, and equipment destruction**.
> - This project is an **educational and research prototype**. It is **not** a certified, industrially isolated, or revenue-grade utility meter.
> - **No unsafe mains wiring instructions are provided in this documentation.**
> - All initial hardware assembly, code debugging, and sensor calibration should be performed using **safe, low-voltage AC power sources** (such as an isolated 12V AC step-down transformer) or isolated benchtop test equipment before any connection to live electrical panels.
> - Never adjust wiring, sensors, or jumpers on an energized board.

> [!IMPORTANT]
> ### Energy & Power Terminology
> The current hardware utilizes an **ACS712** current sensor and a **ZMPT101B** voltage sensor. Because the prototype measures Voltage RMS and Current RMS independently without sampling the simultaneous phase angle ($\phi$) or true power factor ($\cos\phi$):
> - **Voltage RMS ($V_{\text{RMS}}$):** Measured in **Volts (V)**.
> - **Current RMS ($I_{\text{RMS}}$):** Measured in **Amperes (A)**.
> - **Apparent Power ($S = V_{\text{RMS}} \times I_{\text{RMS}}$):** Measured in **Volt-Amperes (VA)**, not True/Real Power in Watts (W).
> - **Estimated Apparent Energy:** Measured in **Volt-Ampere hours (VAh)** or **kilo-Volt-Ampere hours (kVAh)**, not actual active energy in kilowatt-hours (kWh).
> 
> ### Estimated Cost & Tariff Calculation Assumption
> Any estimated billing cost generated by the system is calculated under the explicit assumption that the electrical load operates at **near-unity power factor ($\text{PF} \approx 1.0$)**, or applies a nominal tariff rate directly to Apparent Energy ($\text{kVAh}$) strictly for learning and estimation purposes. It must **never** be interpreted as utility-meter billing accuracy.

## 2. Introduction & Architectural Philosophy

The **Smart Energy Monitoring System** is an IoT platform designed to interface physical analog electrical measurements with an enterprise web architecture.

### What is System Architecture?
System architecture is the conceptual blueprint defining the structure, boundaries, responsibilities, and communication mechanisms across all components of a software application. Rather than coupling hardware drivers, database logic, and user interfaces into an unmaintainable monolith, architecture establishes **independent, loosely coupled layers** governed by clear interfaces.

### Why Divide the Project into Layers?
1. **Separation of Concerns:** Each layer solves problems exclusively within its domain. The ESP32 handles analog acquisition and digital signal processing; Spring Boot handles business validation and calculations; MySQL handles persistence; the frontend handles visualization.
2. **Independent Testability:** The backend can be tested with simulated HTTP payloads without physical hardware attached. The frontend can be verified with mock JSON endpoints.
3. **Security:** Microcontrollers deployed in the field are physically vulnerable and must never possess database credentials or direct database network access.
4. **Modularity:** Swapping out a visualization library, changing database engines, or updating microcontroller hardware can be achieved without rewriting the remaining layers.

## 4. Division of Energy Responsibilities

To ensure data consistency, the system assigns distinct, non-overlapping roles to the ESP32 and the Backend:

```
┌────────────────────────────────────────────────────────────────┐
│                      ESP32 (EDGE COMPUTATION)                  │
│                                                                │
│  - Measures instantaneous Voltage RMS (V)                      │
│  - Measures instantaneous Current RMS (A)                      │
│  - Calculates Apparent Power: S = V_rms * I_rms (VA)           │
│  - Calculates LOCAL INCREMENTAL Apparent Energy:               │
│      ΔVAh = S * (Δt_seconds / 3600.0)                          │
│                                                                │
│  * The ESP32 does NOT maintain authoritative long-term totals  │
│    or billing records.                                         │
└───────────────────────────────┬────────────────────────────────┘
                                │ Transmits (V, I, S, ΔVAh)
                                ▼
┌────────────────────────────────────────────────────────────────┐
│                 BACKEND (AUTHORITATIVE MASTER)                 │
│                                                                │
│  - Validates all incoming measurements                         │
│  - Persists instantaneous raw records to MySQL                 │
│  - Accumulates incremental ΔVAh into AUTHORITATIVE rolling:    │
│      • Hourly apparent energy summaries (kVAh)                 │
│      • Daily apparent energy summaries (kVAh)                  │
│      • Monthly apparent energy summaries (kVAh)                │
│  - Applies tariff pricing to calculate Estimated Cost          │
│  - Detects threshold violations and logs Fault Events          │
└────────────────────────────────────────────────────────────────┘
```

By making the Backend the single source of truth for rolling aggregations, the system avoids synchronization bugs caused by microcontroller reboots, Wi-Fi drops, or rollover in embedded integer counters.

## 5. Network Protocol & Communication Choices

### REST Polling vs. WebSocket
- **Initial Implementation (Phase 4): REST Polling**
  - The frontend client uses the standard JavaScript `fetch()` API to poll `GET /api/v1/measurements/latest?deviceId=SEM-ESP32-001` every 2 to 3 seconds.
  - *Why REST polling first:* Simple to implement, stateless, easy to inspect in standard browser dev tools, and requires no complex connection state management or heartbeat pings on the backend.
- **Future Enhancement: WebSocket**
  - WebSocket provides a persistent, full-duplex TCP channel allowing the backend to push new measurements to the browser immediately upon ingestion.
  - Documented as an advanced optimization for later phases after the core REST pipeline is stable.

### HTTP vs. HTTPS Security Model
- **Development / Local Prototype:**
  - Plain HTTP/1.1 is used across the local network between the ESP32, Spring Boot, and the browser.
  - *Security Clarification:* Plain HTTP is completely **unencrypted** and sends data in cleartext. It is acceptable solely for local lab development and testing.
- **Production Deployment Standard:**
  - Production deployments must mandate **HTTPS (TLS/SSL encryption)** on all endpoints to prevent eavesdropping and packet tampering.
  - Devices must authenticate using pre-shared API tokens in HTTP headers (`X-Device-Token`) or mutual TLS (mTLS).
  - Browser users must authenticate using secure tokens (JWT) or authenticated sessions.

## 6. End-to-End Data Flow

1. **AC Waveform Sensing:** ACS712 detects magnetic flux from current flow; ZMPT101B steps down and conditions the voltage waveform.
2. **ADC Sampling on ESP32:** ADC1 pins (GPIO34, GPIO35) sample the analog signals at high frequency over full AC cycles ($50\text{ Hz}$).
3. **RMS Calculation:** Firmware computes discrete Root-Mean-Square over complete cycles:
   $$V_{\text{RMS}} = \sqrt{\frac{1}{N}\sum_{i=1}^{N}(v_i - v_{\text{midpoint}})^2} \times \text{ScaleFactor}_V \quad (\text{V})$$
   $$I_{\text{RMS}} = \sqrt{\frac{1}{N}\sum_{i=1}^{N}(i_i - i_{\text{midpoint}})^2} \times \text{ScaleFactor}_I \quad (\text{A})$$
4. **Apparent Power & Local Incremental Energy:**
   - Apparent Power: $S = V_{\text{RMS}} \times I_{\text{RMS}}$ in Volt-Amperes (VA).
   - Incremental Apparent Energy: $\Delta \text{VAh} = S \times \frac{\Delta t_{\text{seconds}}}{3600}$.
5. **JSON Payload Construction:** Formats telemetry JSON in ESP32 RAM.
6. **HTTP POST Dispatch:** Sends `POST /api/v1/measurements` via Wi-Fi to Spring Boot.
7. **REST Controller Ingestion:** Spring Boot parses the HTTP payload into `MeasurementRequestDTO`.
8. **Bean Validation:** Rejects invalid ranges ($V < 0$, $I < 0$, null device ID) with HTTP `400 Bad Request`.
9. **Service Layer Processing:** Verifies device registration, detects electrical anomalies/faults, accumulates incremental apparent energy, and computes estimated cost from active tariffs.
10. **Repository Persistence:** Hibernate generates parameterized SQL `INSERT` statements to write the row to the `measurements` table in MySQL.
11. **Confirmation Response:** Backend returns HTTP `201 Created` to the ESP32.
12. **Frontend REST Polling:** Browser executes periodic `fetch('/api/v1/measurements/latest?deviceId=SEM-ESP32-001')`.
13. **JSON Response Dispatch:** Backend returns the latest validated reading as HTTP `200 OK`.
14. **Dashboard Visualization:** JavaScript updates DOM readout cards (V, A, VA, kVAh) and pushes new data points to Chart.js line charts.

## 8. Conceptual Communication Contracts

### Contract 1: Ingestion API (ESP32 $\rightarrow$ Backend)
- **Method & Path:** `POST /api/v1/measurements`
- **Request Headers:**
  - `Content-Type: application/json`
  - `X-Device-Id: SEM-ESP32-001`
- **Conceptual Request Body:**
  ```json
  {
    "deviceId": "SEM-ESP32-001",
    "voltageRms": 230.4,
    "currentRms": 1.42,
    "apparentPower": 327.17,
    "incrementalApparentEnergy": 0.0908,
    "samplingDurationSeconds": 1.0,
    "timestamp": 1774175400
  }
  ```
- **Conceptual Success Response:**
  - `HTTP/1.1 201 Created`
  ```json
  {
    "status": "SUCCESS",
    "message": "Measurement recorded",
    "recordedId": 48201
  }
  ```

### Contract 2: Real-Time Status (Frontend $\rightarrow$ Backend)
- **Method & Path:** `GET /api/v1/measurements/latest?deviceId=SEM-ESP32-001`
- **Conceptual Success Response:**
  - `HTTP/1.1 200 OK`
  ```json
  {
    "deviceId": "SEM-ESP32-001",
  ```

## 9. Conceptual Database Entities (Phase 2 Preview)

1. **`Device`:** Hardware registry. Columns: `device_id` (`SEM-ESP32-001`), name, location, status (`ACTIVE`, `INACTIVE`), registered timestamp.
2. **`Measurement`:** Primary time-series telemetry table. Columns: `id`, `device_id`, `voltage_rms` (V), `current_rms` (A), `apparent_power` (VA), `incremental_apparent_energy` (VAh), `recorded_at`.
3. **`EnergySummary`:** Authoritative pre-aggregated rollups. Columns: `id`, `device_id`, `summary_type` (`HOURLY`, `DAILY`, `MONTHLY`), `total_apparent_energy` (kVAh), `estimated_cost`, `period_start`, `period_end`.
4. **`Tariff`:** Electricity pricing schedules. Columns: `id`, `rate_per_kvah`, `currency`, `effective_from`, `effective_to`.
5. **`CalibrationConfig`:** Sensor calibration parameters. Columns: `id`, `device_id`, `voltage_multiplier`, `voltage_offset`, `current_sensitivity_mv_per_a`, `current_zero_offset`.
6. **`FaultEvent`:** Audit log for abnormal conditions. Columns: `id`, `device_id`, `fault_type` (`OVER_VOLTAGE`, `OVER_CURRENT`, `VOLTAGE_SAG`), `trigger_value`, `occurred_at`.
7. **`User`:** Dashboard access credentials. Columns: `id`, `username`, `password_hash`, `role` (`ADMIN`, `VIEWER`), `created_at`.
